## Що змінилося порівняно з версією на Zynq PS

У коді — рівно одна функція, `InitInterrupts`. Решта переноситься дослівно:
`AdvanceRunningLight`, `PollKeys`, `ApplySpeed`, `TimerCallback`, таблиця
періодів, антидребезг. Вимога «та сама логіка коду» виконується буквально.

```c
/* Zynq PS:    XScuGic + XSetupInterruptSystem, id taken from driver config
 * MicroBlaze: XIntc + explicit exception registration
 */
XIntc_Initialize(&g_intc, INTC_ID);
XIntc_Connect(&g_intc, TIMER_INTR_ID,
              (XInterruptHandler)XTmrCtr_InterruptHandler, &g_timer);
XIntc_Start(&g_intc, XIN_REAL_MODE);
XIntc_Enable(&g_intc, TIMER_INTR_ID);

Xil_ExceptionInit();
Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_INT,
                             (Xil_ExceptionHandler)XIntc_InterruptHandler,
                             &g_intc);
Xil_ExceptionEnable();
```

У MicroBlaze немає GIC, тому в block design з'явився окремий блок
`axi_intc`, а `XSetupInterruptSystem` замінено явною реєстрацією обробника
виняткової ситуації.

У залізі зникли три речі, які раніше давав PS.

**Такт.** Джерелом став кварц 50 МГц на `N18` (`PL_CLK_50M`) — той самий, який
у першому завданні не використовувався взагалі. `FCLK_CLK0` більше немає, тому
тактовий сигнал тепер потребує власного констрейнта.

**Скид.** Додався `Processor System Reset`. Його входи `dcm_locked` і
`aux_reset_in` підтягнуті до одиниці константами: перший означає «такт
стабільний», другий — «додаткового скиду немає». Незаведений `dcm_locked`
тримав би систему у вічному скиді, причому без жодного повідомлення.

**UART.** Ось тут головна відмінність. USB-UART плати розведений на
`PS_MIO14`/`PS_MIO15` — це виводи процесорної підсистеми, з PL до них не
дотягнутися фізично. Без PS консоль через CH340 недоступна в принципі.
Замість неї використано UART всередині MicroBlaze Debug Module: у настройках
`mdm_1` увімкнено `Enable UART`, у BSP `stdin`/`stdout` вказують на `mdm_1`,
і вивід іде через той самий JTAG-кабель у консоль Vitis.

## Block design

| IP | Призначення |
|----|-------------|
| `microblaze_0` | ядро, без кешу, 64 КБ локальної пам'яті |
| `microblaze_0_axi_intc` | контролер переривань |
| `mdm_1` | відладковий модуль, він же UART через JTAG |
| `rst_clk_50m_50M` | Processor System Reset |
| `microblaze_0_axi_periph` | SmartConnect, шість master-портів |
| `axi_gpio_0` | 4 біти — світлодіоди |
| `axi_gpio_1` | 4 біти — кнопки |
| `axi_gpio_2` | 1 біт — перемикач напрямку |
| `axi_timer_0` | два незалежні 32-бітні таймери |

Частота 50 МГц обрана свідомо: MicroBlaze без кешу на speed grade -1
закривається за таймінгами з запасом, а виграшу від 100 МГц у цій задачі
немає. Побічна користь — константа `AXI_CLK_HZ` у коді залишилася такою
самою, як у версії на Zynq PS, де `FCLK_CLK0` теж було 50 МГц.

Виділення: `interrupt` таймера заведено в `In0` блока `Concat`, тому номер
переривання в `XIntc` дорівнює нулю.

## Розподіл таймерів

Без змін відносно першого завдання. Обидва таймери живуть в одному
`axi_timer` і поділяють одну лінію переривання:

| Таймер | Період | Дія |
|--------|--------|-----|
| Timer 0 | змінний, 5 с … 0.1 с | крок доріжки |
| Timer 1 | фіксований, 5 мс | опитування входів і антидребезг |

Окремий таймер опитування потрібен не для зручності: якби кнопки опитувалися
з переривання кроку, на найповільнішій швидкості вони відгукувалися б раз на
п'ять секунд.

Швидкість задає апаратура — зміна зводиться до запису нового значення в
регістр `TLR0`. `while(1)` у `main()` порожній, програмних затримок немає.

## Симуляція

Behavioral simulation усього проєкту з реальним `.elf`, підключеним через
`Tools → Associate ELF Files` (колонка Simulation).

Головна складність тут не технічна, а арифметична: крок доріжки в робочій
прошивці триває від 0.1 до 5 секунд, тобто до 250 мільйонів тактів на один
крок. Симулювати таке неможливо за розумний час.

Розв'язання — окрема збірка `.elf` з `-DSIM_BUILD`, де ті самі вісім рівнів
швидкості виражені в тактах замість секунд:

```c
#ifdef SIM_BUILD
#define POLL_PERIOD     (AXI_CLK_HZ / 100000u)      /* 10 us */
#define DEBOUNCE_TICKS  2u
static const u32 kStepPeriods[] = {
    2000u, 1600u, 1200u, 800u, 400u, 200u, 100u, 40u
};
#else
/* ... periods in seconds ... */
#endif
```

Логіка при цьому одна й та сама — відрізняються тільки числа.

Друга особливість: `xil_printf` у симуляції може заблокуватися назавжди.
MDM UART не має JTAG-хоста, який вичитував би FIFO, тому буфер передачі
переповнюється і програма зупиняється, не дійшовши до основного циклу.
Діагностичний вивід у симуляційній збірці компілюється в порожнечу.

### Testbench

Testbench інстанціює повну обгортку `z7_light_microblaze_wrapper`, генерує
такт 50 МГц, знімає скид і імітує натискання кнопок.

Полярності відрізняються від типового прикладу: скид і всі входи активні
низьким, тому «відпущена кнопка» — це одиниця:

```verilog
// Buttons are active low: press pulls the line to zero.
task press_button(input integer index);
    begin
        btn_drv[index] = 1'b0;
        #PRESS_NS;
        btn_drv[index] = 1'b1;
        #SETTLE_NS;
    end
endtask
```

Кнопку треба тримати довше, ніж вікно антидребезгу, інакше натискання не
зарахується — це та сама логіка, що й на залізі, просто масштаб інший.

Замість фіксованої паузи на завантаження прошивки testbench чекає на першу
появу one-hot патерна. Тут є пастка чотиризначної логіки: до того, як
програма виконає `XGpio_SetDataDirection`, виводи перебувають у стані `z`,
а `z !== 0`, тому наївна умова `led !== 4'b0000` спрацьовує одразу на старті.
Чекати доводиться саме на конкретні значення:

```verilog
wait (led_tri_io === 4'b0001 || led_tri_io === 4'b0010 ||
      led_tri_io === 4'b0100 || led_tri_io === 4'b1000);
```

### Перелік перевірок

| Сценарій | Що підтверджує |
|----------|----------------|
| завантаження прошивки | MicroBlaze стартує, GPIO ініціалізовано |
| початковий хід | горить рівно один світлодіод, доріжка рухається |
| перемикач у зворотне | напрямок змінюється на ходу |
| перемикач назад | напрямок повертається |
| BTN0 | швидкість зростає |
| BTN1 | швидкість спадає |
| BTN2 | доріжка зупиняється |
| BTN2 вдруге | рух продовжується з тієї ж позиції |
| BTN3 | скид до початкових значень |

Прошивка оживає приблизно через 78 мкс модельного часу, повний сценарій
завершується на 761 мкс.

## Зовнішня обв'язка

Та сама макетна плата й ті самі виводи, що в завданні 1. Додалися лише такт
і скид.

| Сигнал | Пін | Роз'єм | Примітка |
|--------|-----|--------|----------|
| `clk_50m` | N18 | — | кварц 50 МГц, PL-домен |
| `reset_n` | P16 | — | розпаяна кнопка K3, активна низьким |
| `led_tri_io[0]` | V15 | JP1-31 | активний високий |
| `led_tri_io[1]` | W15 | JP1-32 | |
| `led_tri_io[2]` | P14 | JP1-33 | |
| `led_tri_io[3]` | R14 | JP1-34 | |
| `btn_tri_io[0]` | L19 | JP2-31 | швидше |
| `btn_tri_io[1]` | L20 | JP2-32 | повільніше |
| `btn_tri_io[2]` | F19 | JP2-33 | стоп / продовжити |
| `btn_tri_io[3]` | F20 | JP2-34 | скид налаштувань |
| `sw_tri_io[0]` | M19 | JP2-35 | напрямок руху |

Використання розпаяної кнопки K3 під скид системи залишає всі чотири кнопки
на макетній платі під функції доріжки.

## Запуск

1. Vivado: `Generate Bitstream`, далі `Export Hardware` з увімкненим
   **Include bitstream**
2. Vitis: створити платформу, у настройках BSP виставити `stdin`/`stdout`
   на `mdm_1`, зібрати платформу, потім застосунок
3. Джампер J1 — у положення **JTAG**
4. `Run → Launch Hardware`. У конфігурації запуску прапорці `Run ps7_init`
   і `Run Ps7 Post Init` мають бути **зняті** — вони належать Zynq PS, якого
   в цьому дизайні немає
5. Вивід — у консолі Vitis через MDM

Симуляція: `Run Simulation → Run Behavioral Simulation`, далі `run all` у
Tcl-консолі. Значення `xsim.simulate.runtime` за замовчуванням дорівнює 1 мкс,
чого не вистачає навіть на завантаження прошивки.


Повний лог — `simulation_log.txt`, waveform — `simulation.png`, робота на
реальному залізі — `demo.mp4`.
