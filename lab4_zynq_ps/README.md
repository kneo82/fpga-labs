# Біжуча доріжка (Zynq PS, AXI GPIO, AXI Timer)

Завдання 1 домашнього завдання. Один запалений світлодіод переміщується по колу
чотирма позиціями; період кроку задає AXI Timer, напрямок — перемикач,
швидкість і зупинку — кнопки.

Перевірено на реальному залізі: плата MicroPhase Z7-Lite, XC7Z010-1CLG400.

## Block design

| IP | Призначення |
|----|-------------|
| `processing_system7_0` | Cortex-A9, DDR3, UART на MIO14/15, `IRQ_F2P` |
| `axi_gpio_0` | 4 біти, вихід — світлодіоди |
| `axi_gpio_1` | 4 біти, вхід — кнопки |
| `axi_gpio_2` | 1 біт, вхід — перемикач напрямку |
| `axi_timer_0` | два незалежні 32-бітні таймери |

Власного RTL у проекті немає. Уся логіка виконується на PS, а PL містить лише
стандартні IP — AXI GPIO тут не логіка, а міст: набір регістрів і буферів.
Процесор пише слово в `GPIO_DATA`, виводи повторюють молодші біти. Сам зсув,
вибір напрямку й реакція на кнопки відбуваються в обробнику переривання.

`FCLK_CLK0` = 50 МГц тактує всю AXI-обв'язку. Кварц 50 МГц на `N18` у цьому
проекті не використовується взагалі — він живить тільки PL-домен, а `FCLK_CLK0`
синтезує PLL всередині PS із кварцу 33.333 МГц. Збіг чисел випадковий.

Три окремі екземпляри AXI GPIO замість двох каналів на одному — щоб входи й
виходи не ділили регістр напрямку. Займає трохи більше логіки, зате помилка в
номері каналу стає неможливою: скрізь канал 1.

## Розподіл таймерів

Обидва таймери живуть в одному `axi_timer` і поділяють одну лінію переривання
в `IRQ_F2P`:

| Таймер | Період | Дія |
|--------|--------|-----|
| Timer 0 | змінний, 5 с … 0.1 с | крок доріжки |
| Timer 1 | фіксований, 5 мс | опитування входів і антидребезг |

Окремий таймер опитування потрібен не для зручності. Якби кнопки
опитувалися з переривання кроку, на найповільнішій швидкості вони відгукувалися б
раз на п'ять секунд — зовні це виглядає як несправність. Розділення знімає
проблему повністю, і при цьому обидва таймери залишаються апаратними.

`XTmrCtr_InterruptHandler` сам визначає, який з двох таймерів спрацював,
підтверджує переривання й викликає колбек із номером таймера. Розбір зводиться
до одного `if`:

```c
static void TimerCallback(void *callbackRef, u8 timerNumber)
{
    if (timerNumber == TMR_STEP) {
        AdvanceRunningLight();
    } else if (timerNumber == TMR_POLL) {
        PollKeys();
    }
}
```

## Швидкість задає апаратура

Вимога завдання — «швидкість визначає AXI Timer, не програмна затримка циклом».
Це означає, що інтервал відлічує лічильник, а не процесор:

```c
static void ApplySpeed(void)
{
    XTmrCtr_Stop(&g_timer, TMR_STEP);
    XTmrCtr_SetResetValue(&g_timer, TMR_STEP, kStepPeriods[g_speedIndex]);
    XTmrCtr_Reset(&g_timer, TMR_STEP);
    XTmrCtr_Start(&g_timer, TMR_STEP);
}
```

Зміна швидкості — це один запис у регістр `TLR0`. Далі кварц відлічує сам,
незалежно від того, чим зайнятий процесор, і з точністю до такту.

`while(1)` у `main()` порожній. Усе відбувається в контексті переривань —
програмних затримок у коді немає жодної.

Вісім рівнів швидкості зберігаються в таблиці, обчисленій від тактової частоти:

```c
static const u32 kStepPeriods[] = {
    AXI_CLK_HZ * 5u,        /* 5.00 s */
    AXI_CLK_HZ * 4u,        /* 4.00 s */
    ...
    AXI_CLK_HZ / 10u        /* 0.10 s */
};
```

Вирази від `AXI_CLK_HZ`, а не готові числа: при зміні `FCLK_CLK0` правиться
одна константа, і всі періоди перераховуються на етапі компіляції. Найдовший
період — 250 млн тактів при межі `u32` у 4.29 млрд, запас сімнадцятикратний.

## Переривання без жорстко прописаних ідентифікаторів

`XSetupInterruptSystem` бере `IntrId` і `IntrParent` безпосередньо з
конфігурації драйвера:

```c
XSetupInterruptSystem(&g_timer, (void *)XTmrCtr_InterruptHandler,
                      g_timer.Config.IntrId, g_timer.Config.IntrParent,
                      XINTERRUPT_DEFAULT_PRIORITY);
```

Альтернатива — прописати `XPAR_FABRIC_AXI_TIMER_0_INTR` вручну, але в
SDT-потоці ці макроси називаються по-різному між релізами. Читання з конфігурації
позбавляє проекту прив'язки до версії інструментів.

Побічна користь: якщо `interrupt` не підключений до `IRQ_F2P` у block design,
`IntrId` дорівнює `65535` — заглушці «переривання немає». Це видно в діагностиці
одразу, замість мовчазної відмови.

## Антидребезг

Механічна кнопка дає 5–30 переходів за 1–20 мс. Фільтрація виконується
програмно, у перериванні Timer 1: рівень приймається лише після чотирьох
стабільних відліків підряд по 5 мс, тобто через 20 мс.

Реакція — на фронт натискання, відпускання ігнорується:

```c
if (level != 0u) {
    OnKeyPressed(i);
}
```

Апаратного фільтра на платі немає, і на зовнішній обв'язці конденсаторів теж
немає — так зроблено свідомо, антидребезг у RTL суперечив би вимозі тримати
логіку в PS.

## Зовнішня обв'язка

Світлодіоди, кнопки й перемикач зібрані на макетній платі.

**Світлодіоди — активний високий рівень.** Вивід FPGA → резистор 1 кΩ → анод →
катод → GND. Розпаяні на платі світлодіоди ввімкнені навпаки (анод на
`VCC_3V3`, активний низький), але для коду зручніше, коли `0b0001` означає
«горить LED0» — інакше довелося б писати `~pattern` скрізь.

| Сигнал | Пін | JP1 |
|--------|-----|-----|
| `led_tri_io[0]` | V15 | 31 |
| `led_tri_io[1]` | W15 | 32 |
| `led_tri_io[2]` | P14 | 33 |
| `led_tri_io[3]` | R14 | 34 |
| GND | — | 30 |

**Кнопки й перемикач — активний низький рівень.** Вивід FPGA → резистор 100 Ω →
кнопка → GND.

| Сигнал | Пін | JP2 | Роль |
|--------|-----|-----|------|
| `button_tri_io[0]` | L19 | 31 | швидше |
| `button_tri_io[1]` | L20 | 32 | повільніше |
| `button_tri_io[2]` | F19 | 33 | стоп / продовжити |
| `button_tri_io[3]` | F20 | 34 | скид до початкових значень |
| `sw_tri_io[0]` | M19 | 35 | напрямок руху |
| GND | — | 30 | |

Рівень «1» у відпущеному стані забезпечує внутрішня підтяжка, оголошена в
`.xdc`:

```tcl
set_property -dict {PACKAGE_PIN L19 IOSTANDARD LVCMOS33 PULLUP true} [get_ports {button_tri_io[0]}]
```

Підтяжка — властивість блока вводу-виводу, а не логіки: у Verilog її описати
неможливо, Vivado бере атрибут із констрейнта й зашиває в бітстрім. Без цього
рядка вхід повисне, і довгі перемички на макетній платі почнуть ловити наводки.

Резистор 100 Ω послідовно з кнопкою — не струмообмеження, а захист: якщо вивід
помилково опиниться сконфігурованим як вихід, струм обмежиться 33 мА замість
короткого замикання. Так само зроблено на самій платі (R81 у схемі `PS_KEY1`).

Розпаяні `PS_LED1` (E6) і `PS_KEY1` (B5) не використовуються — вони сидять на
MIO і через AXI GPIO недоступні в принципі.

Обов'язкові для Zynq-7000 рядки наприкінці `.xdc`, без яких генерація бітстріму
падає на перевірці DRC:

```tcl
set_property CFGBVS VCCO [current_design]
set_property CONFIG_VOLTAGE 3.3 [current_design]
```

## Керування

- **Перемикач** — напрямок: відпущений вперед, замкнений на GND назад
- **BTN0 / BTN1** — швидкість: 5 / 4 / 3 / 2 / 1 / 0.5 / 0.25 / 0.1 с
- **BTN2** — зупинка й продовження з тієї ж позиції
- **BTN3** — скид: позиція LED0, швидкість 1 с, рух увімкнено

Напрямок читається в момент кроку, а не запам'ятовується — перемикач діє одразу,
без очікування наступного циклу.

## Запуск

1. Vivado: `Generate Bitstream`, далі `File → Export → Export Hardware` з
   увімкненим **Include bitstream**
2. Vitis: зібрати платформу, потім застосунок
3. Джампер J1 — у положення **JTAG**
4. Термінал на COM-порту CH340, 115200 8N1
5. `Run → Launch Hardware`, прапорець «Use FSBL flow» **знятий**

Каталоги `ps7_cortexa9_0/` і `zynq_fsbl/` усередині платформи в git не включені:
вони повністю генеруються командою Build із `.xsa` і займають близько півтори
тисячі файлів чужого коду драйверів.
