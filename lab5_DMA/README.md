# Прийом кадру через DMA (MicroBlaze, AXI4-Stream, AXI4-Full)

Домашнє завдання після заняття 12, на базі проєкту 3. Дані кадру 320x200
надходять ззовні дизайну по 8 біт за такт на власній частоті, пакуються в
32-бітні слова і через AXI DMA записуються в `axi4_full_ram`. Прийом
починається не після reset, а лише після натискання кнопки.

Перевірено в behavioral-симуляції з реальним `.elf`.

## Розрахунок об'єму пам'яті

320 x 200 = 64 000 пікселів по 8 біт = 64 000 байт.

У 32-бітних словах: 64 000 / 4 = **16 000 слів**.

Округлено до степеня двійки: `MEM_DEPTH = 16384`, `ADDR_WIDTH = 16`,
тобто 64 КБ адресного простору. Перевірка по коду `axi4_full_ram`: індекс
масиву формується як `addr[ADDR_WIDTH-1:2]`, тобто `addr[15:2]` -- 14 біт,
16384 комірки. Сходиться.

У `Address Editor` обидва майстри -- MicroBlaze і DMA -- бачать пам'ять за
однією адресою `0xC0000000` з діапазоном 64K. Різні адреси означали б, що
DMA пише в одне місце, а програма читає з іншого.

## Модуль frame_rx

```
зовнішнє джерело          frame_rx                  AXI4-Stream
 pix_clk  ──┐      ┌──────────────────┐
 pix_data ──┼─────▶│ пакувальник      │──▶ M_AXIS ──▶ AXI DMA ──▶ axi4_full_ram
 pix_valid ─┘      │ async FIFO       │               (S2MM)
                   │ лічильник втрат  │
                   └────────▲─────────┘
                            │ start
                     AXI GPIO ◀── MicroBlaze ◀── AXI GPIO (кнопка)
```

### Два тактові домени

Зовнішнє джерело живе на власному кварці, AXI-обв'язка -- на своєму. Це і
є та "синхронізація", про яку йдеться в завданні: половина коду модуля
присвячена саме перетину доменів.

| Елемент | Призначення |
|---------|-------------|
| `xpm_cdc_single` x3 | одиночні біти: `start`, скид, `frame_done` |
| `xpm_fifo_async` | дані, 33 біти завширшки |
| `xpm_cdc_gray` | лічильник втрат, 32 біти |

Для багаторозрядного лічильника звичайний синхронізатор не годиться: при
переході `0x0FFF -> 0x1000` змінюються тринадцять біт одночасно, і приймач
може побачити будь-яке проміжне значення. Код Грея змінює рівно один біт за
інкремент, тому в найгіршому випадку видно або старе значення, або нове.

### Порядок байтів -- little-endian

Перший прийнятий байт потрапляє в `tdata[7:0]`. Це не питання смаку:
AXI за специфікацією little-endian, `axi4_full_ram` пише слово без
перестановок, а `Xil_In32` поверне його так само. Будь-який інший порядок
вимагав би уявної перестановки на кожному кроці налагодження.

Видно на `middle.png`: пікселі `48 49 4a 4b` дають слово `4b4a4948`.

### Тридцять третій біт FIFO

FIFO має ширину 33 біти: додатковий біт позначає останнє слово кадру і їде
разом із даними.

Напрошується простіше рішення -- лічильник на стороні читання, який виставляє
`tlast` на слові 15 999. Воно ламається при першій же втраті: якщо три слова
відкинуто, лічильник дорахує до 15 999, а слів прийде 15 997, і `tlast` не
встане ніколи. DMA чекатиме вічно.

Мітка, сформована там само, де створюється слово, від втрат не залежить.

```verilog
fifo_din <= {is_last, pix_data, word_shift};
```

### Переповнення FIFO

Сигналу `ready` в бік джерела не передбачено -- воно видає дані "на певній
частоті" й зупинитися не вміє. Отже вибір лише між "втратити слово" і
"зіпсувати потік". Модуль втрачає і рахує:

```verilog
if (fifo_full) begin
    drop_cnt <= drop_cnt + 32'd1;
end else begin
    fifo_wr_en <= 1'b1;
    fifo_din   <= {is_last, pix_data, word_shift};
end

word_cnt <= word_cnt + 1;   // поза if/else: рахує позицію в кадрі
```

`word_cnt` зростає незалежно від того, записали слово чи втратили: він
відстежує **позицію в кадрі**, а не кількість відправлених слів. Інакше
`is_last` встав би не на тому слові.

У симуляції лічильник залишився нульовим навіть при джерелі, що працює на
повній швидкості без пауз -- див. `end.png`.

## Програма MicroBlaze

Порядок операцій визначає працездатність:

```c
/* 1 */ XAxiDma_SimpleTransfer(&g_dma, RAM_BASE, FRAME_BYTES, XAXIDMA_DEVICE_TO_DMA);
/* 2 */ XGpio_DiscreteWrite(&g_gpioStart, CH_ONLY, 1u);
/* 3 */ while (XAxiDma_Busy(&g_dma, XAXIDMA_DEVICE_TO_DMA)) { }
/* 4 */ XGpio_DiscreteWrite(&g_gpioStart, CH_ONLY, 0u);
```

**DMA озброюється першим.** Запис довжини в регістр і є командою "почати":
DMA піднімає `tready` і чекає даних. Зворотний порядок втратив би початок
кадру -- модуль почав би складати слова у FIFO, а вичитувати їх не було б
кому.

**Крок 4 обов'язковий.** `frame_rx` тригериться наростаючим фронтом, тому без
повернення в нуль наступне натискання кнопки не дало б нового фронту.

Кнопка обробляється програмним антидребезгом: лічильник зростає, поки рівень
тримається, і скидається при будь-якому дребезгу. Перший цикл чекає
**відпускання** -- без нього кнопка, затиснута в момент reset, запустила б
прийом одразу.

## Симуляція

`tb_frame_rx.v` перевіряє модуль **окремо**, без MicroBlaze і DMA. Саме там
зосереджена вся нетривіальна логіка, і цикл налагодження тут -- секунди
замість хвилин.

| Сценарій | Що підтверджує |
|----------|----------------|
| дані до `start` | модуль їх ігнорує, `tvalid` не піднімається |
| повний кадр, приймач готовий | коректне пакування little-endian |
| `tlast` | рівно на останньому слові |
| `dropped_words` | нуль, коли приймач встигає |
| приймач гальмує | втрати фіксуються лічильником |

Результат -- `frame_rx_Test_Log.txt`, усі перевірки PASS.

`tb_system.v` перевіряє всю систему з реальним `.elf`. Кадр повного розміру:
64 000 тактів `pix_clk` -- близько 2.2 мс модельного часу, менше двох хвилин
реального. Зменшувати кадр не знадобилося.

### Чому в testbench немає ієрархічних посилань

Початкова версія чекала на внутрішні сигнали (`wait (dut...frame_rx_0.start)`)
і читала масив пам'яті напряму. `xelab` 2026.1 падає з
`EXCEPTION_ACCESS_VIOLATION` на будь-якому такому зверненні в цьому проєкті --
crash dump компілятора, не помилка коду. Виніс посилання в окремий `wire` не
допоміг.

Тому синхронізація побудована лише на затримках, виміряних з реального
прогону: прошивка опитує кнопку приблизно раз на 2 мкс, антидребезг вимагає
ста відліків, тобто близько 200 мкс на фазу. Взято потрійний запас.

Перевірка результату винесена у waveform: `tdata` на момент `tlast`,
`frame_done` і `dropped_words` кажуть більше, ніж вивід у консоль.

### Результат

`start.png` -- на 864.8 мкс `start` піднімається. Кнопка натиснута, антидребезг
пройдено, DMA озброєно. `pix_valid` ще нуль: модуль чекає.

`middle.png` -- потік. `pix_data` `48 49 4a 4b` дає `m_axis_tdata = 4b4a4948`,
`tvalid` пульсує раз на чотири піксельні такти, `m_axi_s2mm_wvalid` пише в
пам'ять.

`end.png` -- завершення:

```
m_axis_tlast   = 1
m_axis_tdata   = fffefdfc
frame_done     = 1
dropped_words  = 00000000
start          = 0
```

Останнє слово `0xfffefdfc` -- це пікселі 63996..63999, бо `63999 & 0xFF = 0xFF`.
`frame_done` піднято, `start` програма вже зняла, отже вийшла з
`XAxiDma_Busy`: DMA завершив передачу штатно.

## Виправлення в axi4_full_ram

Модуль із прикладів довелося змінити. При `MEM_DEPTH = 256` він синтезувався
без зауважень, при 16384 -- ні:

```
[Synth 8-3391] Unable to infer a block/distributed RAM for 'mem_reg'
because the memory pattern used is not supported. Failed to dissolve the
memory into bits because the number of bits (524288) is too large.
```

Причина: звернення до масиву були всередині блоків з **асинхронним** скидом
(`negedge s_axi_aresetn`). Block RAM у 7-й серії асинхронного скиду вихідного
регістра не підтримує. 8 Кбіт синтезатор розкладав у LUT і проблеми не бачив,
512 Кбіт зобов'язані лягти в BRAM.

Порада з повідомлення (`dissolveMemorySizeLimit`) тут непридатна: вона
розклала б 524288 біт у тригери, яких на XC7Z010 фізично немає.

Виправлення -- винести доступ до масиву в окремий блок без скиду, залишивши
автомати як були:

```verilog
always @(posedge s_axi_aclk) begin
    if (mem_we) begin
        mem[mem_waddr] <= s_axi_wdata;
    end
    if (mem_re) begin
        s_axi_rdata <= mem[mem_raddr];
    end
end
```

Тайминг не змінився: `s_axi_rdata` защіпується за тим самим фронтом і за тією
самою умовою, просто в іншому блоці. Вміст пам'яті не скидається -- і не має:
BRAM ініціалізується з бітстріму.

Після виправлення: **33.5 блока BRAM з 60**, LUTRAM 908 (внутрішнє MicroBlaze
і SmartConnect, не масив).

## Налаштування, без яких не працює

**Width of Buffer Length Register = 17** у AXI DMA. За замовчуванням 14, тобто
максимум 16 383 байти. Потрібно 64 000. При 14 бітах DMA мовчки обрізає
команду до молодших розрядів -- ні помилки, ні попередження.

**`create_clock` для обох тактових сигналів.** Без них імплементація звітує
"all timing constraints are met", але це порожня заява: 30 788 кінцевих точок
не мали жодного такту, щодо якого їх можна виміряти, і просто не аналізувалися.
Після додавання констрейнтів кількість проаналізованих точок зросла з 312 до
31 030, WNS практично не змінився (11.2 нс при періоді 20 нс).

**`set_clock_groups -asynchronous`** між доменами: перетин обробляє FIFO, а не
аналізатор, інакше були б хибні порушення.

## Відомі зауваження

**REQP-1839** (20 попереджень DRC): сигнали `mem_we` / `mem_re` формуються
автоматами з асинхронним скидом і керують входами `ENARDEN` блочної пам'яті.
При знятті скиду можливе спотворення вмісту. Для симуляції нерелевантно;
правильне виправлення -- перевести автомати на синхронний скид.

**`Could not open 'C' for writing`** виникало кілька разів під час синтезу --
блокування файлів у каталозі проєкту осиротілими процесами `xvlog`/`xelab`.
Лікується перезапуском і режимом `Global` для Generate Output Products.

## Запуск

1. Vivado: відкрити `lab5_DMA/lab5_DMA.xpr`. Репозиторії IP -- `Custom_IP`
   і `Axi4_full_ram`
2. `Generate Bitstream`, далі `Export Hardware` з **Include bitstream**
3. Vitis: зібрати платформу (`stdout` на `mdm_1`), потім застосунок
4. Vivado: `Tools -> Associate ELF Files`, колонка **Simulation**
5. `Settings -> Simulation -> xsim.simulate.runtime` = `all`
6. `Run Behavioral Simulation`, відкрити `tb_system_behav.wcfg`

Симуляція модуля окремо: встановити `tb_frame_rx` як top у проєкті
`Custom_IP` і запустити -- кілька секунд.
